# Lectio: карта API и заметки для фронтенда

Проверено по коду 26.10.2026. Рабочая справка для разработки фронта и следующих
сессий агента. Описывает **существующее поведение**, а предложения вынесены отдельно.
В репозитории сейчас только бэкенд; требования к экранам ниже — вывод из его
возможностей, а не утверждённый дизайн или спецификация продукта.

Проверены все 48 операций из сгенерированного OpenAPI: 47 с `/api/v1` и `/health`.
Дополнительно прочитаны схемы, сервисы, права, обработчики ошибок, worker и
интеграционные тесты. OpenAPI получен локально через `app.openapi()`.
Набор pytest не прогонялся. После составления справки выполнена ручная проверка
на запущенном локальном API с настоящими моделями — результаты в разделе 15.

## 1. Общий контракт

- Локальный адрес API по README: `http://localhost:8000`.
- Все прикладные пути ниже **относительно `/api/v1`**. Исключения: `/health`,
  `/docs`, `/redoc`, `/openapi.json` находятся в корне приложения.
- UUID передаются строками. Даты — строки ISO 8601 с часовым поясом.
- Таймкоды и длительности — числа в **секундах**, допускают дробную часть.
- JSON для обычных запросов; `multipart/form-data` для видео и аватара.
  Для `FormData` не задавать `Content-Type` вручную: браузер добавит boundary.
- Массивы возвращаются напрямую: `[]`, без `{items, total}`.
- `204` означает отсутствие тела: не вызывать `response.json()`.
- `202` означает принятие фоновой задачи, а не завершение обработки.
- Ответы проходят через middleware с заголовком `X-Request-ID`; его полезно
  сохранять при ошибке. Входящий `X-Request-ID` принимается длиной до 128 символов.
- Списки обычно не содержат полей текущего пользователя. Для страницы лекции есть
  отдельный агрегат `GET /lectures/{lecture_id}/me`.

### Доступ

В таблицах: **П** — публично, **В** — нужен Bearer access-токен,
**У** — преподаватель и право управлять объектом, **Т** — любой преподаватель.

- Роли: `student` и `teacher`. Роль выбирается при регистрации; по умолчанию
  `student`. Отдельного подтверждения роли преподавателя сейчас нет.
- Преподаватель управляет своими курсами/лекциями и объектами без владельца
  (`owner_id: null`, например импортированными CLI).
- Добавление/перенос лекции в курс требует права управлять и этим курсом.
- Запись на курс **не ограничивает доступ**: каталог, видео, расшифровка, конспект,
  поиск и Q&A публичны. Нет закрытых курсов, оплаты, приглашений или публикации.
- Личные функции доступны обеим ролям: прогресс, запись на курс, избранное,
  закладки, история поиска, дашборд.
- Только `/search` использует необязательную авторизацию: без токена работает,
  с валидным — ещё пишет историю; с просроченным/невалидным токеном вернёт `401`.
  Остальные публичные прикладные ручки пользователя из Bearer не извлекают.

### Ошибки

Бизнес-ошибки и HTTP-ошибки обычно имеют вид `{"detail": "Lecture not found"}`.
Ошибки валидации FastAPI: `{"detail": [{"loc": [...], "msg": "...", "type": "...", ...}]}`.
Единого машинного `error_code` нет. Не привязывать логику фронта к английским текстам.

| HTTP | Смысл / реакция фронта |
| --- | --- |
| `400` | Бизнес-ограничение, например закладка дальше конца лекции. |
| `401` | Нет входа / access истёк / refresh недействителен. Попробовать refresh один раз, затем вход. |
| `403` | Нет роли или права владельца. Скрывать недоступные действия, но обрабатывать отказ сервера. |
| `404` | Объект/файл отсутствует; чужая закладка тоже считается отсутствующей. |
| `409` | Конфликт: email занят, лекция ещё обрабатывается, недоступна перегенерация. |
| `413` | Превышен лимит файла. |
| `415` | Неподдерживаемый тип медиа или аватара. |
| `422` | Неверные UUID, поля, длины, диапазоны; показывать ошибки формы. |
| `429` | Лимит регистрации/входа; `Retry-After` содержит секунды ожидания. |
| `503` | LLM недоступна при Q&A. Дать повторить запрос. |

Это ошибки, выявленные по реализации; OpenAPI автоматически описывает не все
бизнес-ответы. Необработанные серверные ошибки не имеют гарантированного JSON-формата.

## 2. Авторизация и сессия

| Метод и путь | Доступ | Принимает | Ответ и назначение |
| --- | --- | --- | --- |
| `POST /auth/register` | П | JSON: `email`, `password`, `first_name`, `last_name`, `role?` | `201 AuthResponse`, сразу авторизует и ставит refresh-cookie. Занятый email → `409`. |
| `POST /auth/login` | П | JSON: `email`, `password` | `200 AuthResponse` + refresh-cookie. Неверные данные / неактивный пользователь → `401`. |
| `POST /auth/refresh` | Cookie | Без JSON; cookie `refresh_token` | `200 AccessTokenResponse` + новая cookie. Старая одноразовая и перестаёт работать. Нет/истёк refresh → `401`, cookie очищается. |
| `POST /auth/logout` | Cookie, необязательна | Без JSON | `204`; отзывает текущий refresh и очищает cookie. Без cookie тоже успешен. |
| `POST /auth/logout-all` | В | Без JSON | `204`; отзывает все refresh-сессии пользователя и очищает текущую cookie. |
| `GET /auth/me` | В | Без параметров | `200 UserResponse`; загрузка текущего профиля. |

Ограничения регистрации: email валидный; пароль **8–128** символов; имя и фамилия
после trim — **1–100**. Для входа пароль **1–128**. Email сохраняется в нижнем регистре.

```ts
type Role = "student" | "teacher";
type PublicUserResponse = {
  id: string;
  first_name: string;
  last_name: string;
  role: Role;
  avatar_url: string | null;
};
type UserResponse = PublicUserResponse & { email: string; created_at: string };
type AccessTokenResponse = { access_token: string; token_type: "bearer" };
type AuthResponse = AccessTokenResponse & { user: UserResponse };
```

Access передавать как `Authorization: Bearer <access_token>`. По умолчанию он
действует 30 минут; TTL не возвращается отдельным полем. Refresh живёт 30 дней
(обе длительности конфигурируются). Refresh отсутствует в JSON и недоступен JS:
cookie `HttpOnly`, `SameSite=Lax`, `Path=/api/v1/auth`, `Secure=true` по умолчанию.

Лимиты по умолчанию: вход — 50 запросов/IP и 10/email за 15 минут;
регистрация — 10/IP за час. Значения настраиваются в `core/config.py`.

**Фронту:** access держать в состоянии приложения; при старте попробовать refresh,
потом `/auth/me`. Объединять параллельные refresh в один запрос: токен ротируется,
несколько одновременных запросов с одной cookie могут дать `401`. После успешного
refresh повторить исходный запрос один раз, без бесконечного цикла. При logout
очищать access, профиль и персональные кеши. Уже выданные access-токены logout
и logout-all немедленно не отзывают: они действуют до истечения срока.

### Важное ограничение CORS / cookie

В `main.py` заданы разрешённые origins, методы и заголовки, **но нет
`allow_credentials=True`**. Поэтому одного `credentials: "include"` на фронте
недостаточно для полноценной cookie-сессии между разными origins.

Варианты интеграции:

1. Общий origin: dev-proxy / reverse proxy для `/api` и фронта.
2. Разные origins: доработать CORS с credentials и конкретными разрешёнными origins;
   клиенту отправлять auth-запросы с `credentials: "include"`.

По умолчанию в allowlist только `http://localhost:5173` и
`http://127.0.0.1:5173`. Настройки для HTTP-разработки и production надо согласовать
с `REFRESH_COOKIE_SECURE`. `SameSite=Lax` также нужно учитывать при разных sites:
одни CORS-настройки не решают ограничения cookie.
Сейчас доступны JS-заголовки `X-Request-ID`, `Content-Range`, `Accept-Ranges`;
`Retry-After` в expose_headers отсутствует — при разных origins его чтение
потребует доработки.

## 3. Профиль и аватар

| Метод и путь | Доступ | Принимает | Ответ и назначение |
| --- | --- | --- | --- |
| `PATCH /users/me` | В | JSON: `first_name?`, `last_name?` | `200 UserResponse`; частичное обновление имени. Пустой объект ничего не меняет. Явный `null` → `422`. |
| `PUT /users/me/avatar` | В | Multipart: обязательный `file` | `200 UserResponse` с `avatar_url`; заменяет аватар. |
| `DELETE /users/me/avatar` | В | Без тела | `204`; удаляет аватар. |
| `GET /users/{user_id}` | П | UUID пользователя в пути | `200 PublicUserResponse`; имя, роль, аватар преподавателя/пользователя. Email и дата регистрации не раскрываются. Неактивный/отсутствующий → `404`. |
| `GET /users/{user_id}/avatar` | П | UUID в пути | `200` файл картинки; можно использовать в `<img>`. Без аватара → `404`. |

Аватары: PNG, JPEG, WebP; тип определяется по начальным байтам файла, не по
расширению/Content-Type. Лимит по умолчанию **5 MiB**, настраивается
`MAX_AVATAR_MB`. При `avatar_url: null` фронт показывает инициалы/заглушку.
URL после замены может остаться тем же: предусмотреть обновление изображения
без старого браузерного кеша, например query-параметром версии на стороне фронта.
Изменения email, пароля, роли и удаления аккаунта через API нет.

## 4. Курсы и запись

| Метод и путь | Доступ | Принимает | Ответ и назначение |
| --- | --- | --- | --- |
| `POST /courses` | Т | JSON: обязательный `title`, необязательный `description` | `201 CourseResponse`; новый курс владельца. |
| `GET /courses` | П | Query: `owner_id?: UUID` | `200 CourseResponse[]`; все курсы или курсы преподавателя. Без пагинации, старые сначала (`created_at`, затем `id` ASC). |
| `GET /courses/{course_id}` | П | UUID в пути | `200 CourseResponse`; курс со статистикой, **без массива лекций**. Нет курса → `404`. |
| `DELETE /courses/{course_id}` | У | Без тела | `204`; удаляет курс. Лекции остаются и получают `course_id: null`. |
| `PUT /courses/{course_id}/enrollment` | В | Без тела | `204`; записывает на курс, повторная запись успешна. Нет курса → `404`. |
| `DELETE /courses/{course_id}/enrollment` | В | Без тела | `204`; отписывает, отсутствие записи не ошибка; существование курса проверяется. Прогресс лекций отдельно не удаляется. |
| `GET /me/courses` | В | Без параметров | `200 EnrolledCourseResponse[]`; именно курсы, на которые пользователь записан, с прогрессом; последние записи сначала. |

Название курса после trim — **1–300** символов. `description` — строка или `null`,
явного ограничения длины в схеме нет.

```ts
type CourseResponse = {
  id: string;
  owner_id: string | null;
  title: string;
  description: string | null;
  created_at: string;
  lectures_count: number;
  total_duration_seconds: number;
};
type EnrolledCourseResponse = CourseResponse & {
  enrolled_at: string;
  completed_lectures: number;
  progress: number; // 0..1, доля завершённых лекций по количеству
};
```

Статистика курса включает все его лекции, в том числе необработанные;
неизвестная длительность не добавляет секунд. Для пустого курса прогресс `0`.
«Мои курсы преподавателя» загружаются через `/courses?owner_id=<me.id>`;
`/me/courses` показывает записи на обучение, а не авторство.
**PATCH/PUT курса нет**: переименовать курс или изменить описание сейчас нельзя.

## 5. Лекции: загрузка, каталог, управление, медиа

| Метод и путь | Доступ | Принимает | Ответ и назначение |
| --- | --- | --- | --- |
| `POST /lectures` | Т | Multipart: `file` обязателен; `title?` до 300 символов; `course_id?: UUID` | `202 LectureResponse` со статусом `pending`; файл уже принят, обработка ставится в очередь. |
| `POST /lectures/import` | Т | JSON: `url` обязателен (HTTP/HTTPS), `title?`, `course_id?` | `202 LectureResponse`; скачивание и обработка выполняются worker. Валидный URL не гарантирует успешный импорт. |
| `GET /lectures` | П | Query: `limit=50` (1–200), `offset=0` (≥0), `course_id?`, `status?`, `owner_id?` | `200 LectureResponse[]`; новые сначала (`created_at`, затем `id` DESC). Фильтры применяются совместно. |
| `GET /lectures/{lecture_id}` | П | UUID в пути | `200 LectureResponse`; карточка, текущий этап и прогресс обработки. Нет лекции → `404`. |
| `PATCH /lectures/{lecture_id}` | У | JSON: `title?`, `course_id?` | `200 LectureResponse`; переименование и перенос между доступными курсами. |
| `DELETE /lectures/{lecture_id}` | У | Без тела | `204`; удаляет лекцию, её файлы и связанные записи по FK. |
| `POST /lectures/{lecture_id}/reprocess` | У | Без тела | `202 LectureResponse`; сбрасывает этап в `pending`, прогресс в 0, ошибку в `null`, ставит обработку заново. Активная обработка → `409`. |
| `GET /lectures/{lecture_id}/video` | П | UUID в пути; HTTP `Range` по необходимости | `200` полный файл / `206` часть файла. Нет локального файла → `404`. |

Форматы upload: `.mp4`, `.m4v`, `.webm`, `.mov`, `.mkv`, `.mp3`, `.m4a`, `.wav`,
`.ogg`. Допуск определяется расширением; успешная загрузка не гарантирует,
что ffmpeg сможет прочитать содержимое. Лимит по умолчанию **4096 MiB**,
настраивается `MAX_UPLOAD_MB`. Браузерная воспроизводимость исходного
контейнера/кодека не гарантирована: API отдаёт сохранённый файл.

Для upload пустой/пробельный title заменяется именем файла без расширения
(затем fallback `Untitled lecture`). Для JSON import/PATCH непустое title после
trim — **1–300** символов. У import без title сначала используется URL, worker
может заменить его заголовком скачанного видео.

PATCH: пропущенное поле не меняется; `course_id: null` убирает лекцию из курса;
`title: null` игнорируется. `{}` — допустимый запрос без изменений.
Reprocess доступен только для `ready`/`failed`; это перезапуск всего конвейера,
а не только конспекта.

```ts
type LectureStatus =
  | "pending" | "downloading" | "extracting_audio" | "transcribing"
  | "indexing" | "summarizing" | "ready" | "failed";
type LectureResponse = {
  id: string;
  course_id: string | null;
  owner_id: string | null;
  title: string;
  source_type: "upload" | "url";
  source_url: string | null;
  duration_seconds: number | null;
  language: string | null;
  status: LectureStatus;
  progress: number; // 0..1: обработка текущего этапа, НЕ просмотр
  error: string | null;
  created_at: string;
  updated_at: string;
  video_url: string | null;
  subtitles_url: string | null;
};
```

Файловые пути `video_path`/`avatar_path` наружу не выдаются. URL медиа и аватара
относительные, начинаются с `/api/v1/...`. Если фронт и API на разных origins,
разрешать их относительно **origin бэкенда**, а не текущей страницы.
Не добавлять `/api/v1` повторно.

### Состояния обработки для UI

Обычная последовательность:
`pending → downloading (для импорта) → extracting_audio → transcribing → indexing → summarizing → ready`.
При ошибке основного конвейера — `failed` с `LectureResponse.error`.

- `progress` относится к текущему этапу и сбрасывается при смене этапа.
  Нельзя показывать его как точный процент всей задачи; не у каждого этапа
  есть дробные обновления.
- На первом запуске worker может скачивать веса модели уже в статусе
  `transcribing`: отдельного статуса/прогресса загрузки модели нет. У MLX
  распознавание тоже не отдаёт промежуточный прогресс — только итоговый.
  Долгий `transcribing` с `progress: 0` сам по себе не означает зависание.
- `202` возвращается до выполнения задачи; нужен отдельный запущенный worker.
  ID задачи, позиция в очереди и ETA в ответах отсутствуют.
- Получать изменения polling-запросами к `/lectures/{lecture_id}`;
  SSE/WebSocket нет. Предложение для фронта: раз в 2–5 секунд на видимой странице,
  с остановкой при `ready`/`failed` и отменой при уходе со страницы.
- `video_url` появляется, когда у лекции есть сохранённый путь к файлу, независимо
  от готовности остальных функций. Он сам по себе не подтверждает наличие
  файла/поддержку кодека браузером; обрабатывать ошибку плеера.
- При `summarizing` и `ready` уже доступны расшифровка, субтитры и поиск.
- Сбой генерации конспекта обычно **не делает лекцию failed**: она становится
  `ready`, а причина лежит в `SummaryResponse.error`. Это отдельная ошибка.

## 6. Расшифровка, субтитры и конспект

| Метод и путь | Доступ | Принимает | Ответ и назначение |
| --- | --- | --- | --- |
| `GET /lectures/{lecture_id}/segments` | П | UUID в пути | `200 SegmentResponse[]`; вся расшифровка по `position` ASC, без пагинации. Не `summarizing`/`ready` → `409`. |
| `GET /lectures/{lecture_id}/subtitles.vtt` | П | UUID в пути | `200 text/vtt; charset=utf-8`; субтитры для `<track>`. Та же проверка готовности. |
| `GET /lectures/{lecture_id}/summary` | П | UUID в пути | `200 SummaryResponse`; Markdown-конспект, дерево оглавления и термины. До генерации может вернуть `summary: null`, пустые массивы; не требует `ready`. |
| `POST /lectures/{lecture_id}/summary` | У | Без тела | `202`, полезных данных в теле нет (JSON `null`); ставит задачу перегенерации. Разрешён только для `ready`, иначе `409`. |

Для всех этих ручек несуществующая лекция → `404`.

```ts
type SegmentResponse = {
  id: string;
  position: number; // начиная с 0
  start_seconds: number;
  end_seconds: number;
  text: string;
};
type ChapterResponse = {
  id: string;
  title: string;
  start_seconds: number;
  subsections: ChapterResponse[];
};
type KeyTerm = {
  term: string;
  definition: string;
  start_seconds: number | null;
};
type SummaryResponse = {
  lecture_id: string;
  status: LectureStatus; // статус лекции, не отдельной summary-задачи
  summary: string | null; // Markdown
  error: string | null; // summary_error, отдельно от ошибки всей лекции
  chapters: ChapterResponse[];
  key_terms: KeyTerm[];
};
```

Фронту: клики по реплике/главе/термину перематывают плеер; термин без времени
нельзя превращать в таймкод. У API сегменты реплик, word-level таймкоды наружу
не выдаются. Редактирования текста расшифровки, конспекта и глав через API нет.
Markdown отображать безопасным renderer с отключённым/очищенным raw HTML.

После POST summary статус меняет **worker**, а не HTTP-обработчик. Первый GET
может ещё вернуть старый `ready` и старый конспект. Сейчас нет job ID или
версии генерации, поэтому такое состояние нельзя надёжно трактовать как
завершение новой задачи. См. список доработок ниже.

## 7. Поиск, история и Q&A

| Метод и путь | Доступ | Принимает | Ответ и назначение |
| --- | --- | --- | --- |
| `GET /search` | П / optional Bearer | Query: обязательный `q` (trim, 1–500); `lecture_id?: UUID`, `course_id?: UUID`, `limit=10` (1–50) | `200 SearchHit[]`; гибридный поиск по содержимому обработанных лекций. У вошедшего пользователя сохраняет запрос в историю. |
| `GET /me/search-history` | В | Query: `limit=10` (1–50) | `200 RecentSearch[]`; уникальные строки запросов, последние сначала. Повтор поднимает строку вверх. |
| `DELETE /me/search-history` | В | Без тела | `204`; очищает всю личную историю. |
| `POST /qa` | П | JSON: `question`, `lecture_id?`, `course_id?`, `history?` | `200 AnswerResponse`; ответ LLM в Markdown со ссылками `[1]`, `[2]` на источники. Без стриминга. |

Область поиска и Q&A: без ID — вся база; с `lecture_id` — одна лекция; с
`course_id` — курс. Если задать оба ID, применяются **оба фильтра**: это
пересечение, а не приоритет одного. Несовпадающие лекция/курс дадут пустую выдачу.
Несуществующий явно заданный объект → `404`; явно заданная ещё не готовая
лекция → `409`. Глобальная/курсовая выдача просто исключает лекции вне
`summarizing`/`ready`.

```ts
type SearchHit = {
  chunk_id: string;
  lecture_id: string;
  lecture_title: string;
  start_seconds: number;
  end_seconds: number;
  text: string;
  highlight: string; // HTML-фрагмент с <mark>...</mark>
  score: number;
};
type RecentSearch = { query: string; searched_at: string };
type ChatMessage = { role: "user" | "assistant"; content: string };
type QuestionRequest = {
  question: string;
  lecture_id?: string | null;
  course_id?: string | null;
  history?: ChatMessage[];
};
type AnswerResponse = { answer: string; sources: SearchHit[] };
```

Поиск возвращает фрагменты, а не каталог по названию. Нет offset/total и
гарантированного порога релевантности. `score` — ранжирующая величина, её шкала
меняется при включении reranker; не отображать как процент уверенности.
`highlight` формируется с экранированием исходного текста и тегами `<mark>`;
при выводе HTML ограничить разрешённую разметку этим тегом. `text` — обычный текст.

Q&A: `question` после trim — **1–2000** символов, `history` — до **20** сообщений,
каждый `content` до **8000** символов. Порядок истории — от старого к новому;
новый вопрос передавать в `question`. Допустимы только роли user/assistant.
Бэкенд сам выбирает до 6 фрагментов для контекста; `sources[n - 1]` соответствует
ссылке `[n]` в ответе. Фронт превращает ссылки в переходы к нужной лекции и секунде.

Сессий/сохранения чата на сервере нет: фронт хранит историю и отправляет её при
каждом запросе, обрезая под лимиты. При отсутствии найденных фрагментов возвращается
обычный `200` с поясняющим `answer` и `sources: []`. При недоступной LLM — `503`.
Ожидание может быть долгим: базовый timeout LLM по умолчанию 300 секунд и разрешён
один retry клиента LLM; это не жёсткий верхний предел всего HTTP-запроса.
Нужны индикатор ожидания и отмена ожидания на фронте; отмена fetch не гарантирует
остановку генерации на сервере.

История поиска не возвращает сохранённые `lecture_id`/`course_id` — повтор запроса
нельзя автоматически восстановить в исходной области. GET search пишет историю
даже при пустой выдаче, если пользователь авторизован; Q&A её не пишет.
Поэтому автопоиск на каждый символ будет засорять историю: предпочтителен submit
или осмысленный debounce и отмена устаревших запросов.

## 8. Прогресс просмотра и «продолжить»

| Метод и путь | Доступ | Принимает | Ответ и назначение |
| --- | --- | --- | --- |
| `GET /lectures/{lecture_id}/progress` | В | UUID в пути | `200 ProgressResponse`; откуда продолжить. Без записи: 0 секунд, `completed: false`, `updated_at: null`. Нет лекции → `404`. |
| `PUT /lectures/{lecture_id}/progress` | В | JSON: обязательный `position_seconds ≥ 0`, `completed?: boolean / null` | `200 ProgressResponse`; сохраняет последнюю позицию и признак завершения. Нет лекции → `404`. |
| `GET /me/continue-watching` | В | Query: `limit=10` (1–50) | `200 ContinueWatchingItem[]`; незавершённые лекции с позицией > 0, последние обновлённые сначала. |

```ts
type ProgressResponse = {
  lecture_id: string;
  position_seconds: number;
  completed: boolean;
  updated_at: string | null;
};
type ContinueWatchingItem = {
  lecture: LectureResponse;
  position_seconds: number;
  updated_at: string;
};
```

Если длительность известна, позиция обрезается до конца лекции. По умолчанию
достижение **90%** помечает лекцию завершённой; перемотка назад отметку не снимает.
`completed: true` завершает явно; `completed: false` снимает отметку даже если
переданная позиция уже ≥90%; следующий автоматический save на такой позиции
может завершить снова. `completed: null` работает как пропущенное поле.
Это **последняя позиция**, не максимальная просмотренная секунда и не учёт
реального времени: перемотка вперёд тоже может завершить лекцию.

Фронту: восстанавливать позицию после готовности метаданных плеера, сохранять
примерно раз в 5–10 секунд и на паузе/уходе, не на каждом `timeupdate`.
Это рекомендуемый интервал UI, сервер его не задаёт. Учитывать, что запрос при
закрытии вкладки может не успеть. Запись прогресса не требует enrollment.
Сериализовать отправки, чтобы старый медленный save не затёр новую позицию.

## 9. Избранное и закладки

| Метод и путь | Доступ | Принимает | Ответ и назначение |
| --- | --- | --- | --- |
| `PUT /lectures/{lecture_id}/favorite` | В | Без тела | `204`; добавляет в избранное, повтор успешен. Нет лекции → `404`. |
| `DELETE /lectures/{lecture_id}/favorite` | В | Без тела | `204`; убирает, отсутствие записи/лекции не проверяется. |
| `GET /me/favorites` | В | Без параметров | `200 LectureResponse[]`; последние добавленные сначала, без пагинации. |
| `POST /lectures/{lecture_id}/bookmarks` | В | JSON: `position_seconds ≥ 0`, `note?` | `201 BookmarkResponse`; личная закладка на таймкоде. |
| `GET /lectures/{lecture_id}/bookmarks` | В | UUID в пути | `200 BookmarkResponse[]`; только свои, по секунде ASC, затем дате создания ASC. Нет лекции → `404`. |
| `GET /me/bookmarks` | В | Без параметров | `200 BookmarkWithLectureResponse[]`; все свои, последние созданные сначала, без пагинации. |
| `PATCH /bookmarks/{bookmark_id}` | В | JSON: `position_seconds?`, `note?` | `200 BookmarkResponse`; частичное изменение своей закладки. |
| `DELETE /bookmarks/{bookmark_id}` | В | Без тела | `204`; удаляет свою закладку. Чужая/отсутствующая → `404`. |

```ts
type BookmarkResponse = {
  id: string;
  lecture_id: string;
  position_seconds: number;
  note: string | null;
  created_at: string;
  updated_at: string;
};
type BookmarkWithLectureResponse = BookmarkResponse & { lecture_title: string };
```

`note` обрезается по краям, до **2000** символов; пустая строка сохраняется как
`null`. На PATCH пропуск note оставляет её, `null`/пустая строка очищает.
`position_seconds: null` на PATCH игнорируется. Если длительность известна,
таймкод после конца → `400` (в отличие от progress, который обрезает позицию).
Повторный POST закладки создаёт ещё одну запись, дедупликации нет.

## 10. Дашборд и агрегат страницы лекции

| Метод и путь | Доступ | Принимает | Ответ и назначение |
| --- | --- | --- | --- |
| `GET /me/dashboard` | В | Без параметров | `200 DashboardResponse`; статистика кабинета, 5 лекций «продолжить» и 5 последних уникальных запросов. |
| `GET /lectures/{lecture_id}/me` | В | UUID в пути | `200 LectureStateResponse`; позиция, избранное, запись на курс, права и закладки одним запросом. Нет лекции → `404`. |

```ts
type DashboardResponse = {
  enrolled_courses: number;
  lectures_completed: number;
  lectures_in_progress: number;
  watched_seconds: number;
  favorites: number;
  bookmarks: number;
  lectures_uploaded: number | null; // число своих лекций для teacher, null для student
  continue_watching: ContinueWatchingItem[];
  recent_searches: RecentSearch[];
};
type LectureStateResponse = {
  progress: ProgressResponse;
  is_favorite: boolean;
  is_enrolled_in_course: boolean;
  can_manage: boolean;
  bookmarks: BookmarkResponse[];
};
```

`watched_seconds` — **сумма текущих сохранённых позиций** по лекциям пользователя,
а не фактическое время обучения: повторный просмотр не накапливается, перемотка
меняет показатель. `lectures_in_progress` считает все незавершённые записи
WatchProgress, даже с позицией 0; «продолжить» такие записи исключает.
`lectures_uploaded` считает все лекции с owner_id пользователя, в том числе URL-импорт.

`can_manage` лучше использовать для кнопок лекции вместо повторения логики прав.
Для лекции без курса `is_enrolled_in_course=false`. Саму `LectureResponse` этот
агрегат не включает: нужен также `GET /lectures/{lecture_id}`.

## 11. Системная ручка

`GET /health` — публично, **без `/api/v1`**, ответ `200 {"status":"ok"}`.
Это проверка работы HTTP-приложения, не готовности БД/Redis/worker/ML/LLM.
Swagger `/docs`, ReDoc `/redoc`, схема `/openapi.json` — стандартные страницы
FastAPI, не отдельные продуктовые функции.

## 12. Что должен уметь фронт на текущем API

Ниже — предложенный объём интерфейса, который уже поддерживается сервером.

| Экран / сценарий | Данные и действия | Что учесть |
| --- | --- | --- |
| Гостевой каталог | `/courses`, `/lectures`, фильтры по курсу/автору/статусу | Курсы и материалы открыты; названия и аватары авторов загружать по `owner_id`, кешировать. Нет серверного поиска каталога по title. |
| Регистрация и вход | register/login, выбор роли, восстановление через refresh | Ошибки полей, занятый email, 429, истёкшая сессия; cookie/CORS настроить до интеграции. |
| Личный кабинет | `/auth/me`, `/me/dashboard`, `/me/courses` | Счётчики, продолжить, история запросов; не выдавать watched_seconds за точный трекер времени. |
| Страница курса | `/courses/{course_id}` + `/lectures?course_id=...`; enrollment | Состояние записи получить из `/me/courses`; список лекций отдельно, учесть limit/offset. |
| Просмотр лекции | `/lectures/{lecture_id}`, video, segments, VTT, summary | Плеер, субтитры, синхронная расшифровка, оглавление, термины, обработка/ошибки, поиск в лекции. |
| Личные действия в лекции | `/lectures/{lecture_id}/me`, progress, favorite, bookmarks | Продолжить с позиции, завершить/снять завершение, заметки и таймкоды; гостю предложить вход. |
| Поиск по материалам | `/search`, история поиска | Область: всё/курс/лекция; переход из результата в плеер к start_seconds; пустая выдача и отмена устаревших запросов. |
| Чат по лекции/курсу | `/qa` + history из состояния фронта | Ожидание полного ответа, ссылки на источники, таймкоды, лимиты истории и 503. |
| Избранное и все закладки | `/me/favorites`, `/me/bookmarks` | Открыть лекцию на таймкоде, редактировать/удалить заметку; списки без пагинации. |
| Профиль | `/users/me`, avatar PUT/DELETE | Правка имени/фамилии, загрузка изображения, заглушка, обновление кеша картинки. |
| Кабинет преподавателя | `/courses?owner_id=me.id`, `/lectures?owner_id=me.id` | Это авторский контент, отдельно от enrollment. Создание курса, upload/import, перенос/переименование/удаление лекции, reprocess, regenerate summary. |

### Практические заметки по реализации

1. Общий API-клиент: base URL, JSON/FormData, Bearer, cookie, один refresh,
   корректный разбор `204` и ошибок, отмена запросов и `X-Request-ID`.
2. Разделять три величины: `lecture.progress` — обработка;
   `ProgressResponse.position_seconds` — просмотр; `EnrolledCourseResponse.progress`
   — доля завершённых лекций. Не хранить их в одном поле состояния.
3. Для открытия лекции грузить публичные данные, а `/me` вызывать только при
   авторизации; гостевой просмотр не должен зависеть от личного запроса.
4. Для плеера все переходы из результатов поиска, реплик, глав, терминов,
   закладок и источников Q&A свести к одной операции seek. Deep link с ID лекции
   и секундой — задача роутера фронта; сервер отдельную ссылку не возвращает.
5. После изменений инвалидировать связанные данные: favorite → личный агрегат,
   избранное, dashboard; progress → личный агрегат, continue-watching, мои курсы,
   dashboard; enrollment → мои курсы, личный агрегат, dashboard; bookmarks →
   списки закладок, личный агрегат, dashboard. Изменение состава курса затрагивает
   его статистику и прогресс.
6. Для разрешений лекции использовать `can_manage`; для курса отдельного поля
   нет, текущая логика — teacher и (`owner_id === me.id` или `owner_id === null`).
7. Для каталога лекций без total возможны «загрузить ещё» / следующая страница;
   точное число страниц из этого ответа определить нельзя.
8. У upload отделять прогресс передачи файла от фоновой обработки. Прогресс
   передачи измеряется клиентом; бэкенд возвращает состояние после загрузки.
9. Двойной клик на import/upload/POST bookmark может создать дубликаты.
   Блокировать повторную отправку формы, не повторять такие запросы автоматически
   после неоднозначного сетевого сбоя: idempotency key API не поддерживает.
10. Обрабатывать loading, пустые данные, 401, 403, 404, 409, неудачный upload,
    failed-обработку и отдельную ошибку summary. Null duration/language/media URL
    — нормальны для ещё не обработанной лекции.

## 13. Чего не хватает / что согласовать до фронта

Это **предложения и выявленные ограничения**, не реализованные ручки.

| Приоритет | Возможность / проблема | Зачем фронту и как жить сейчас |
| --- | --- | --- |
| P0 при разных origins | Credentials в CORS и согласованные cookie-настройки | Иначе refresh-сессия браузера не заработает полноценно. Можно начать с общего origin через proxy. |
| P1 | Редактирование курса: title/description | Создать можно, исправить ошибку нельзя. Нужен PATCH курса, если в UI есть редактирование. |
| P1 | Явное состояние задачи перегенерации summary | Сейчас POST не меняет статус сразу, нет task ID / версии / queued-флага. Для надёжного UI нужен подтверждаемый старт и результат конкретной генерации; одного первого ready недостаточно. |
| P1 для больших каталогов | Пагинация и total для списков; поиск по title, сортировка | У courses/favorites/bookmarks/me-courses пагинации нет; lectures имеет только limit/offset. Нынешний semantic search ищет содержание, не названия. |
| P1 при неподдерживаемом медиа | Гарантированно браузерный формат воспроизведения | Upload принимает MKV/MOV/разные кодеки, сервер не гарантирует перекодирование в формат для браузера. Временно ограничить выбор файлов в UI и показывать ошибку плеера. |
| P1 для персональных карточек | Пакетные progress/is_favorite/can_manage для списка лекций | Сейчас личный агрегат только на одну лекцию. Иначе дополнительные запросы на каждую карточку или объединение отдельных личных списков на фронте. |
| P2 | Отдельное состояние enrollment курса | Сейчас для кнопки на странице курса читать весь `/me/courses`; полезен course/me или include в деталях. |
| P2 | Сохранённые чаты и streaming Q&A | Сейчас история на фронте, ответ целиком. Серверное хранение нужно для продолжения между устройствами. |
| P2 | Scope в истории поиска | Без lecture_id/course_id нельзя точно повторить прошлый поиск. |
| P2 | Единые error_code и полное описание ошибок в OpenAPI | Упростят типизацию, локализацию и различение бизнес-состояний. |
| P2 | Публичный конфиг лимитов/возможностей | Сейчас лимиты размера и другие настройки известны только из конфигурации; фронт не может получить актуальные значения через API. |
| P2 по требованиям продукта | Обложки, порядок лекций/разделы курса, описание лекции | Полей/ручек сейчас нет; порядок лекций задаётся датой создания DESC. Не обещать это в макетах без доработки. |
| P2 по требованиям продукта | Восстановление/смена пароля, изменение email, удаление аккаунта | API отсутствует. Не делать работающие на вид формы без серверного сценария. |
| P2 по требованиям продукта | Настоящее время обучения | Сейчас хранится позиция, нет событий просмотра/сессий. Для точной аналитики потребуется отдельный учёт. |

Также нет публичного списка пользователей/преподавателей, редактирования
транскрипта/summary/глав, приватных курсов, отмены фоновой задачи, прогресса
через SSE/WebSocket и отдельной readiness-проверки зависимостей. Реализовывать
их только при соответствующих продуктовых требованиях; для базового фронта
не всё из этого обязательно.

### Что понадобилось исправить в локальном запуске

На этом Mac с Apple Silicon в `.env` были Linux-настройки
`WHISPER_BACKEND=faster_whisper`, `WHISPER_COMPUTE_TYPE=int8_float16`.
В этом backend нет Metal; на CPU данной машины `int8_float16` не поддерживается.
Локальные настройки заменены на:

```env
WHISPER_BACKEND=mlx
WHISPER_COMPUTE_TYPE=default
```

Worker перезапущен, незавершённая лекция автоматически поставлена на обработку
снова. При первом скачивании Whisper завис Xet; обычная HTTP-загрузка с
`HF_HUB_DISABLE_XET=1` завершилась. Веса MLX размером около 1,6 ГБ теперь в кеше.
Также запущен установленный Ollama; модель `qwen3:4b-instruct` уже была скачана.
Исходный код обработки для этого не менялся.

Команды для повторного запуска сервисов после их остановки:

```bash
ollama serve
# В другом терминале:
HF_HUB_DISABLE_XET=1 uv run python -m lectio.worker
# В третьем терминале:
uv run uvicorn lectio.main:app --reload
```

### Как повторить проверку вручную

1. Открыть [Swagger](http://localhost:8000/docs).
2. Вызвать login с email и паролем демо-преподавателя выше.
3. Скопировать `access_token` из ответа, вставить в **Authorize**
   (для HTTP Bearer достаточно самого токена).
4. Загрузить файл через `POST /lectures` или ссылку через `POST /lectures/import`;
   скопировать `id` созданной лекции.
5. По этому ID смотреть статус, видео, segments, summary, выполнять search и qa.
   Для новой лекции дождаться `summarizing`/`ready`, прежде чем проверять поиск.
